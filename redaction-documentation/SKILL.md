# Writing assembly documentation

A good manual lets someone who has never seen the project build it again
alone, without a costly mistake (polarity, burnt component, part printed for
nothing). Write for that reader, not for the user. Write the manual in the
user's language, or in the language they ask for, and reply in their language.

## 1. Before writing: gather, and fill the gaps

Make an inventory of everything the manual will mention: parts, 3D models,
STEP/STL files, Gerber files, datasheets, firmware, photos, tools.

**When an item you mention is missing from the context (no 3D model of a
component, no datasheet, no photo, missing firmware…), do not work around it
silently and do not invent it: offer the user to download it.** For each
one, give the likely source (manufacturer's website, GrabCAD, KiCad library,
GitHub repository), the expected file name and where to put it in the project.
For a simple part, offer as an alternative to model it at standard
dimensions; the choice is the user's.

Why: a manual that describes a part you cannot see anywhere, or a guessed
dimension, is exactly where the reader goes wrong. Example: a DC jack and a
switch missing from the 3D model give assembly views that do not show them.

Facts are checked, not assumed: measure in Fusion (screw length, which way
a housing opens), read the netlist for polarities.
What only the user knows (part printed or salvaged, real assembly order),
ask as multiple-choice questions.

## 2. Structure

Numbered chapters in build order, one Markdown file each
(`docs/00-version.md`, `01-presentation.md`…), assembled into a PDF:

0. Version, reading conventions, revision history
1. Overview, numbered exploded view, duration and difficulty, safety
2. Bill of materials with checkboxes (components, purchases, printed parts,
   fasteners), screws drawn at 1:1 scale, tools
3. Circuit board: ordering, soldering order, polarities
4. 3D printing: settings, orientation, test parts
5. Mechanical assembly, step by step
6. Wiring: diagram + connection table
7. Firmware and first test **with the enclosure open**
8. Closing the enclosure
9. Troubleshooting (symptom → cause → test)

## 3. Techniques that make a manual readable

- **One operation = one step = one image.** The part being fitted in colour,
  the rest in grey, an arrow and a label.
- **One unique reference per part**, identical in the bill of materials, the
  image and the text: PCB references (R1, D1, J2), P = printed, V = screw,
  E = purchased.
- **Step header**: duration, tools, parts (with quantities).
- **Typed callouts, used sparingly**: Note, Caution, Danger, Check.
- **A check at the end of each chapter** (continuity, voltage, play).
- **Announce irreversible actions before** asking the reader to do them.
- **One single colour code** for wires (red +12 V, orange +5 V, black GND).
- Version + history on page 2.

## 4. Illustrations

- 3D views generated **by script** from Fusion (reproducible for the
  next version), document closed without saving afterwards.
- Arrows and labels added by script, with an automatic check that no label
  goes outside the image.
- 2D diagrams (wiring, soldering, 1:1 screws) as SVG generated by script.
- Look at every image produced before including it.

## 5. Deliver

- PDF rebuilt by a project command (for example `python tools/build_pdf.py`,
  a script to write in the project, not provided by this skill), checked page
  by page (contact sheet).
- Flag what is not verified (assumed dimension, 1:1 scale to measure).
